## サポートされるバージョン

本プロジェクトは flake として配布され、**最新の `main` ブランチのみ**がセキュリティ修正を受け取ります。
過去のコミットは個別には維持しません——古いバージョンが必要な場合は fork し、ご自身で維持してください。

| 範囲 | サポート |
|------|---------|
| `main` ブランチ（最新） | ✅ セキュリティ修正を受け取る |
| 公開済みの flake 出力（古い世代） | ❌ 最新へ更新してください |
| `dsh-api-balance` サブプロジェクト | 同サブプロジェクトは独自のセキュリティポリシーを未整備です。脆弱性は[本リポジトリ](https://github.com/Kihara777/NixKits/security/advisories/new)へご報告ください。または[独立リポジトリ](https://github.com/Kihara777/dsh-api-balance)を参照 |

## 脆弱性の報告

**セキュリティ問題を公開 issue で報告しないでください。**

以下のいずれかの非公開チャネルをご利用ください：

1. **GitHub の非公開脆弱性報告**（推奨）：<https://github.com/Kihara777/NixKits/security/advisories/new>
2. メール：`npm@g41.moe`

可能な範囲で以下を含めてください：

- 影響を受けるコンポーネント（パッケージ / モジュール / スキル / プラグイン）とファイルパス
- 再現手順または概念実証
- 影響評価（データ読み取り、コード実行、権限昇格、サービス拒否）
- 修正案があればその内容

## 対応期限

本プロジェクトは、**一級視覚障害の証明**を保有する個人が維持しています。
体調により対応速度が影響を受ける場合があります——その現実的な制約をご理解ください。

| 段階 | 目標 |
|------|------|
| 受領確認 | 7 日以内 |
| 初期評価 | 14 日以内 |
| 修正または緩和 | 深刻度と体調により変動。連絡は継続します |

深刻な問題は優先して対応します。長期間応答がない場合は、督促のメールを再度お送りください。

## 既知の設計境界

以下は**脆弱性ではなく**意図された挙動です。報告前にご確認ください：

| 項目 | 説明 |
|------|------|
| `nixkits.dsh.reverseProxy.autoAuth` | 宣言的な**認証不要の入口**。信頼できる LAN でのみ有効化してください。リスクは利用者のネットワーク境界が負担します（`docs/zh/dsh.md` 参照） |
| `sudo` デーモン | root が必要な操作は外部 sudo デーモン経由で実行され記録されます。サンドボックス権限の段階は利用者がセッションごとに明示的に選択し、**既定では一切緩めません** |
| `dsh-api-balance` がブラウザの Local Storage を読む | プラットフォームのセッショントークン取得のため。**既定で有効、無効化可能**。トークンのみを読み、ブラウザ内の他のデータは収集しません。トークンは `0600` で保存されます |
| `/nix/store` 絶対パス | 設定に埋め込んだ store パスは GC 後に無効になります——既知の罠であり脆弱性ではありません。`nixos_cli op=audit-store-paths` で監査できます |

## 評価済みの外部報告（クローズ済みを含む）

以下の報告はすべて**項目ごとに精査**し、証拠を公開して回答済みです。
**掲載しているのは、後続の報告者が同種の問題を再提出せずに済むようにするためです**——
いずれかの結論が誤っていると思われる場合はお知らせください。再評価します。

| 報告 | 主張 | 結論 | 根拠 |
|------|------|------|------|
| PR #4（@anupamme） | `/token`・`/voicepack`・`/tts` にレート制限がない | **誤検出、未マージ** | 説明と diff が不一致（実際に変更されたのは `/query` のみ）。レート制限キーの `x-forwarded-for` はクライアントが偽造可能で、ローカルの同一オリジン RPC はこのヘッダを送らないため、全ローカルトラフィックが単一バケットに集約され利用者自身のパネルを制限してしまう |
| PR #5（@anupamme） | `/query` にリクエストボディのサイズ上限がない | **誤検出、未マージ** | その防御は `readJsonBody` の 64 KiB 上限として既に存在。追加された `content-length` 検査は chunked で回避でき、`text.length` はバイト数ではなく UTF-16 コード単位を数えている |
| issue #1（@begininvoke） | `secrets: inherit` が最小権限に違反する | **誤検出、クローズ** | 被呼び出し側は同一リポジトリ内のローカル workflow（issue が想定した外部ソースではない）。リポジトリの secret は合計 2 つのみで、明示的な受け渡しも `inherit` も集合は完全に同一——攻撃者に利得はない |
| issue #2（@begininvoke） | issue #1 と同じ（バイト単位で完全重複） | **重複、クローズ** | 同上 |

> これらの報告は**ルールとしては概ね事実を突いています**が、脅威モデルが本プロジェクトの配備形態に当てはまりません。
> 私たちは「まず精査し、再現可能な証拠を添えて回答する」という方針で扱っており、無条件に受け入れることはしません。

### 重複投稿について

**上表に既に記載された同一の結論を、新しい証拠なしに再投稿した場合は、本節を指し示してそのままクローズします。**

これはセキュリティ報告を拒否するものではなく、線引きです：

| 受理する | そのままクローズする |
|---------|-------------------|
| 上表に含まれない**新規**の問題 | 上表と同一の結論で、新しい証拠のない重複報告 |
| 上表のいずれかの結論が**誤り**であるとの指摘（再現可能な証拠を添える場合） | 上表に既にある結論の単なる再述 |
| 同じ主題だが**異なる**脅威モデルまたは攻撃経路 | 同一ルールを再度出力した自動スキャン |

**「結論が誤っている」との指摘は常に歓迎します**——上表の 4 件も精査のうえでの判断であり、その根拠自体が誤っていれば訂正します。

### これらがもたらした実際の改善

これらの報告は**2 件の実際の堅牢化**につながりました——報告自体は誤検出でしたが、指し示した方向は追う価値がありました：

| 堅牢化 | 内容 |
|--------|------|
| **`/tts` エンドポイントの SSRF** | どの報告も言及していませんが、エンドポイントを精査する過程で発見：このプロキシは任意の `http(s)` URL を受け取りホストの身分でリクエストを発行し、ユーザー制御の `headers` をそのまま転送していました。修正済み——ループバック / プライベート / リンクローカル / 予約アドレスを拒否し（IPv4-mapped IPv6 を含む）、カスタムリクエストヘッダはホワイトリスト化しました。**当該エンドポイントは `dsh-api-balance` とともに[独立リポジトリ](https://github.com/Kihara777/dsh-api-balance)へ移転しました** |
| **CI の最小権限** | issue を精査する過程で発見：31 のビルド workflow が `permissions` を宣言しておらず、リポジトリ既定（読み書きの可能性あり）を継承していましたが、必要なのは `contents: read` のみでした。すべて更新しました |

**意味するところ**：本リポジトリは報告を歓迎し、真剣に精査します。誤検出は迷惑とは扱いません——上記 4 件の報告は最終的に 2 件の実際の堅牢化につながりました。

## サプライチェーンについて

- 本リポジトリの CI はサードパーティの GitHub Actions を**コミット SHA に固定**しています（浮動タグではありません）
- リポジトリは**いかなる秘密情報も含みません**。認証情報は常に外部に置き、`path:` input 経由で取り込みます
- ビルド成果物は公開の Cachix バイナリキャッシュへ push されます
- ビルド workflow は最小権限を明示的に宣言します（`contents: read`）
