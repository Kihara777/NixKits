## 本ブランチ固有のリスク：意図的に再現不能である

`llama-cpp-ver` は求値のたびに GitHub 上の llama.cpp の**最新リリース JSON** を取り、
`nixpkgs` は `nixos-unstable` を追従し、`flake.lock` は**意図的に提交しない**。つまり：

- 時を変えて `nix build` すると、異なる内容を得る可能性がある；
- 上流が誤ってタグを切るか release が改竄されると、**次の求値がそれを取る**。
  そして「自分が構築したのはこれ」と示す lock が手元に無い；
- CI の成果物も commit から再現できない。

これは**意図的なトレードオフ**である：浮動を一つのパッケージだけのブランチに閉じ込め、
`main` を固定できるようにする。**本ブランチに二つ目のパッケージを足さないこと** ——
浮動面は小さいほど監査しやすい。

## 緩和策

| 措置 | 説明 |
|---|---|
| **内容は上流タグで固定される** | 版は浮動だが、取るのは `releases/latest` のタグであり、同一タグのソース内容は変わらない |
| **hash の変更は review 必須** | 版を上げると overlay の hash も変わる。その diff が人による審査点になる |
| **上流は一つ** | `ggml-org/llama.cpp` は本機推論経路の唯一の上流であり、第二の源を導入しない |
| **CI で上流バイナリを実行しない** | 本ブランチは構築と install のみ。実際に llama.cpp を動かすのは下流の配備 |

## 脆弱性の報告

`main` と同じ：`main` ブランチの `SECURITY.md` を参照 —— 非公開の経路を使い、
**公開 issue を立てないこと**。本ブランチ自身（overlay / module / flake 定義）に
関する報告では、その連絡に「impure ブランチ」と明記してほしい。
